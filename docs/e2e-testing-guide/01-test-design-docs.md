# 第1部: コードを書く前に作る書類

## 1.1 テスト観点表とは何のためにあるか

**観点表(Test Perspective Table)** とは、既存または追加予定のテストを「何を確認しているテストか」という切り口で棚卸しした一覧です。目的は2つ:

1. 新しくテストを追加する前に、既存テストが何をカバーしているかを確認し、**重複を避ける**
2. 一覧化することで、**カバーできていない観点(抜け漏れ)を可視化する**

4アプリはそれぞれ異なるスタイルで観点表を作っていますが、比較すると設計判断の幅がよく見えます。

| アプリ | ドキュメント | スタイル |
|---|---|---|
| documenso | `e2e/TEST_DESIGN.md` | ディレクトリ(機能ドメイン)別テーブル(件数+観点)+ 横断的「設計パターン」章 |
| twenty | `docs/02-test-perspective-table.md` | まず「観点の分類(物差し)」を定義 → ファイル別マッピング → 「観点カバレッジのギャップ」で締める |
| n8n | `docs/TEST_PERSPECTIVE_MATRIX.ja.md` | A〜Iの9大分類(優先度◎◯△つき)。機能だけでなく非機能・AI品質・CI信頼性・テストコード自体の品質まで含む |
| cal.diy | `docs/test-matrix.md` | 「機能×状態・条件×期待結果」の4列表。`feature-design.md`(仕様)・`scenarios.md`(操作手順)と見出しを揃えて相互参照可能にしている |

スタイルは違っても共通する型が1つあります。**「観点」列(何を確認するか)と「実装/参照」列(どのコードがそれを担保しているか)は必ずセットになっている**ことです。観点だけ書いて実装への参照がない観点表は、コードが変わった瞬間に形骸化します。

## 1.2 観点の分類軸の作り方

n8nの `TEST_PERSPECTIVE_MATRIX.ja.md` が持つA〜Iの分類軸は、単一アプリの観点表としては最も体系立っています。骨格として提示し、他アプリがどの軸を(明示的でなくとも)実質的にカバーしているかを対応づけます。

| 軸 | 説明 | 他アプリでの対応例 |
|---|---|---|
| A. 機能テスト観点 | CRUD、UIとAPIの等価性など「何が正しく動くか」 | documenso: ドキュメント/エンベロープCRUD |
| B. UI操作・状態観点 | キャンバス操作、通知、空状態表示など | twenty: 画面遷移・状態遷移 |
| C. 権限・データ分離観点 | ロール別挙動、共有、マルチユーザー同時操作 | documenso: 組織権限階層マトリクス |
| D. 異常系・回復性観点 | DB切断からの回復、想定外入力への耐性 | (documenso/twentyでは薄い領域。1.5節参照) |
| E. 非機能観点 | メモリ消費、描画性能、スループット | (documenso/twenty/cal.diyには専用ディレクトリなし) |
| F. リグレッション観点 | 過去の不具合の再発防止 | n8n: `tests/cli-workflows/`(実際の不具合ワークフローJSONを再生) |
| G. AI出力品質観点 | 生成AIの出力評価(pass/failでなく成功基準判定) | n8n固有。他3アプリにはAI生成機能自体がない |
| H. CI実行・信頼性観点 | シャーディング、フレーキー対策 | documenso: `license`プロジェクトの直列実行 |
| I. テストコード自体の品質観点 | アーキテクチャ適合性([04-code-quality.md](./04-code-quality.md)) | n8nのみ静的解析ツール(janitor)を持つ |

**教材としての要点**: 観点表を作るとき、いきなり機能(A)から書き始めがちですが、C(権限・データ分離)・D(異常系)・I(テストコード品質)は意識しないと抜けやすい軸です。特にI軸(テストコード自体の品質)を観点表の対象に含めているのはn8nだけであり、これは「テストが増えた後」のフェーズで効いてくる視点です。

## 1.3 「機能設計書 → シナリオ → 観点表」の3点セット

cal.diyの `docs/` は3つのドキュメントに役割を分けています(`docs/README.md`)。

| ドキュメント | 役割 | 粒度 |
|---|---|---|
| `feature-design.md` | 仕様書。機能が何を実現し、どんなエッジケースを持つか | 「目的」「主要な仕様/挙動」「エッジケース」の3段構成 |
| `scenarios.md` | 代表的な操作フロー。新しいテストを書くとき、この粒度で書き出すとPage Objectの呼び出し列にそのまま落とし込める | 「1. 〜する。2. 〜を確認する。」という手順書 |
| `test-matrix.md` | 状態・条件 × 期待結果 × 対応するテストケース名の一覧表 | Noつきの表。実際の`test()`タイトルを参照できる |

3つとも**同じカテゴリ構成・同じ見出し(機能名+テストファイルパス)**で揃えられているため、あるテストファイルについて調べたいときに3ドキュメントを横断的に参照できます。これは複数の観点表スタイルを1つのプロジェクトで両立させる実例として参考になります。

重要な運用ルールが `docs/README.md` に明記されています:

> テストが `test.skip` / `test.fixme` でスキップされている、または全体がコメントアウトされている箇所は、その旨を明記しています(未実装/一時無効化と、正式に仕様として確定している内容を混同しないでください)。

実際に `test-matrix.md` には「(スキップ中)」「(現在無効化中)」という注記が随所にあります(例: `overlay-calendar.e2e.ts` は全テストがコメントアウトされており「現状有効なテストケースは存在しない」と明記)。**観点表はテストコードのスナップショットであり要求仕様書ではない**、という位置づけを明確にしておかないと、無効化されたテストが「仕様として確定している」と誤読されるリスクがあります。

## 1.4 権限×データ×操作の総当たりマトリクス設計

複数ユーザー・複数ロールが絡む機能では、「ロール × 対象の可視性 × 操作」の直積をテストケースとして展開するパターンが、documenso・n8n双方で最も件数の多いテスト群を生んでいます。

documenso `TEST_DESIGN.md` 5.2章より:

- `folders/team-account-folders.spec.ts`(66件): ロール(Member/Manager/Admin/Owner) × フォルダ可視性(Everyone/Manager/Admin) × 操作(閲覧/移動/変更)の総当たり
- `organisations/organisation-permission-hierarchy.spec.ts`(18件): メンバー削除・グループ削除・招待再送・組織脱退などをロールの組み合わせで検証
- `api/v2/test-unauthorized-api-access.spec.ts`(217件、最大規模ファイル): エンドポイント×操作(一覧/作成/更新/削除/送信/複製...)ごとに他ユーザー/他チームからのアクセスを検証

n8nでは同じ発想がタグとブラウザコンテキスト分離で表現されています(`fixtures/base.ts`):

```typescript
// n8n: 別ユーザーとして独立したブラウザコンテキストを作る
const member = await api.publicApi.createUser({ email: `member-${nanoid()}@test.com`, ... });
const memberN8n = await n8n.start.withUser(member);
await expect(memberN8n.credentials.cards.getCredential(credentialName)).toBeVisible();
```

**設計判断として持ち帰るべき点**: この種のマトリクステストは件数が爆発的に増える(217件のファイルもある)ため、1テストケース=1直積要素という単純な書き方をすると保守が破綻します。documensoでもn8nでも、直積の「軸」自体(ロール一覧、可視性区分)をコード上の定数・ヘルパーとして共通化し、テスト本体はループまたはパラメタライズで生成する形を取っています。

## 1.5 観点表でよくある抜け漏れパターン

twentyの `02-test-perspective-table.md` 末尾「観点カバレッジのギャップ」がそのまま優れた実例になっています。同ドキュメントは自分たちの観点表を作る過程で見つけた抜け漏れを、いわば「答え合わせ」として書き残しています:

> - **異常系(エラーメッセージ・バリデーション)**: 現状のテストはほぼ正常系のみ。必須項目未入力、不正なメールアドレス形式、重複データなどのエラーハンドリングを確認するテストが見当たらない。
> - **権限差分**: `signup_invite_email.spec.ts` 以外に、Admin/Member等ロール別の閲覧・操作可否を確認するテストが見当たらない(`lib/pom/settings/rolesSection.ts` はPOMとして存在するが、使用しているspecファイルはない)。
> - **設定画面セクション単体のテスト**: 多数のPOMがあるが、専用のspecファイルを持つのは一部の操作のみ。

ここから一般化できる、抜け漏れを見つけるための実践的なチェック方法が2つあります。

1. **正常系だけで異常系(バリデーション、エラーメッセージ)が薄いパターン**を疑う。E2Eは正常系から書き始めがちで、意識しないと異常系は後回しになる。
2. **Page Object(操作の手段)は存在するのにそれを使うspecがない**、という「片方だけ存在する」状態は抜け漏れの強いシグナル。POMが先に作られてテストが追いついていないケースと、逆に一度使われたPOMのspecが削除されて死んでいるケースの両方があり得るので、n8nのjanitorが持つ `dead-code` ルール([04-code-quality.md](./04-code-quality.md) 参照)のような機械的検出とも相性が良い。
