# notes 目次構成 (v2)

最終更新: 2026-08-30

Atlas(`atlas/src/lib/nav.ts`)の第一〜第四階層をすべて確認したうえで、そのまま流用せずnotes向けに再設計したもの。**実際のセクション一覧・URLは`src/lib/nav.ts`が常に正**(本書はその設計意図を記録する計画文書)。

v1は第二階層のスケルトンまでで、Atlasの第三・第四階層(GoFの各分類、Reactの各章、AWS/GCPの個別サービス、業界の中分類など)の行き先が未定のまま抜けていた。移植の済んだ基礎理論・コンピュータ・ネットワーク・データベース・設計は各項に第三階層まで書き足されているが、残る7セクション(実装・フロントエンド・バックエンド・テスト・セキュリティ・インフラ・その他)は一行の見出し案のままだった。v2ではその7セクションについて、Atlasの全ノードを第四階層まで突き合わせ「notesのどこに置くか / 置かないか」を決めきる。

**第一階層の改訂 ― 「実装」を「言語」と「開発の進め方」に分ける**(2026-08-30): 割り当ての結果、`/dev`「実装」に7見出し・47ページが集まった。ここで、12セクションのうち`/dev`だけが工程の名前(設計→実装→テスト)であり、しかもその名前が本来指す中身 ― 画面を書く・APIを書く ― は、フロントエンドとバックエンドを第一階層へ上げた時点で出ていっていることがはっきりした。残ったのは性格の違う2つの塊で、(a)**言語そのもの**(言語の仕組み・JavaScript/TypeScript・並行処理、23ページ)は基礎理論やコンピュータと同じ土台の知識、(b)**工程と道具**(開発プロセス・開発環境・Git/CI/CD・デバッグ、24ページ)は開発を回すための手順にあたる。名前が中身を指すよう2セクションに分け、第一階層は13セクションとする。分量の面でも47ページは設計(56ページ)に次ぐ大きさで、1セクションのままではサイドバーが重い。方針1が戒めているのは「書いてもいない分野を先に並べること」であり、移植対象が確定しているこのケースには当たらない。

## 設計方針

1. 網羅的な資格対策サイトにしない。Atlasは経営・会計・業界まで広がった18セクション構成だが、notesは「実際に学んだ技術を蓄積する場」であり最初から全分野を用意しない
2. 工程軸(Atlasの「開発工程」= 要件定義・レビュー・保守等)と主題軸(設計・テスト等)の二重管理を避ける([`00background/02_lessons-from-atlas.md`](../00background/02_lessons-from-atlas.md)参照)。工程軸の独立セクションは作らず、内容は書くタイミングで該当する主題セクションに寄せる
3. 「本番でどう動かすか」は一つの関心事として、Atlasの「インフラ」「クラウド」「サービス運営」を統合する
4. プログラミング以外の分野(マネジメント・会計・業界等)はあらかじめ複数セクション用意せず「その他」に一本化する。3層分離によりセクション分割はテキスト編集だけで済むため、育った時点で分割すればよい
5. **ナビゲーションは第三階層を最下層とし、URLは第二階層を挟まないフラットな1セグメント**(`/design/paradigm-oop`のように親の名前をハイフンでつなぐ)。Atlasで第四階層だったページは、(a)束ねノードを落として第二階層を増やす か (b)親ページの節として統合する のいずれかで畳む。どちらを選んだかは各セクションの判断欄に書く
6. **束ねノードとページを重複させない**。Atlasには索引ページと役割が重なる子ページ(`セッション・Cookieの全体像`と`セッションとCookie管理`など)が残っていた。notesでは索引ページ本体に統合する

- `nav.ts`の`tree`には**執筆済みのページだけ**を載せる。本書に書かれた見出しは計画であり、ページを書いた時点で`content/pages/`・`routes.ts`・`nav.ts`の3箇所を同時に更新する(教訓「nav.ts記載漏れによる孤立ページ」)
- 束ねノード(ページを持たないラベル)は`href`を持たないノードとして`nav.ts`に書ける。配下のページを1つでも書いたら束ねノードごと追加してよい
- `docs/contents/*.tsx`はAtlasから移す前の下書き置き場であり、`content/pages/`に移して初めて公開対象になる。セクション名やURLがAtlasのまま(例: `Eyebrow`が「情報科学」、`/dev/frontend/...`へのリンク)のものが混ざっているので、移す際に本書の構成へ合わせて直す
- 本書とのズレが出たら`nav.ts`が正。構成を変えるコミットには本書の更新も含める(教訓「設計ドキュメントの陳腐化」)
