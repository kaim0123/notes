# Atlasからの教訓

最終更新: 2026-08-30

## 主要な失敗: 図解不足

Atlasは文章中心になり、視覚的に理解を助ける要素が決定的に不足していた。

### 実態(コードから確認した事実)

- 全516ページ(`atlas/src/content/pages/`)のうち、`Diagram`コンポーネント・`<svg>`・画像のいずれかを使っているページは合計でも130ページ程度(約25%)。残り約4分の3はMarkdown由来の文章・箇条書き・数式・表のみで構成されている
- 執筆済みの教材下書き(`atlas/docs/05content-plan/`配下の`.md`)を見ても同様で、例えば「基数変換」「補数」のような本来は図(位取りの重み、ビット反転の様子、数直線上の範囲など)で示した方が理解しやすい内容が、すべて文章と数式だけで説明されている
- Atlas側に用意されていた`Diagram`コンポーネント(`atlas/src/components/docs/content.tsx`)は、実態としては「枠線+キャプション」を付けるだけの装飾ラッパーであり、それ自体は図を生成しない。中に実際の図(SVGなど)を渡すページが少なかったため、コンポーネントがあっても中身が伴わなかった

### 原因

- 図(SVGやイラスト)を都度手書き・手動作成するコストが高く、文章を書く方が圧倒的に速かったため後回しにされ続けた
- 「後で図を足す」を前提にした結果、実際には足されないまま蓄積した
- 図解専用のワークフロー・ツールが決まっておらず、都度アドホックに作るしかなかった

### これを受けた方針

図解の作成コストを下げ、執筆フローに組み込む。具体策は[`03_diagram-policy.md`](./03_diagram-policy.md)を参照。

## 参考: Atlas自身が記録している構造面の教訓

図解以外にも、Atlasの`docs/03detail-design/site-detail.md`§7「過去の課題と教訓」に、実装が進む中で表面化した問題が記録されている。notesを新規に作る際は、同じ問題を繰り返さないよう初期設計の段階でこれらを踏まえる。

| 課題 | 内容 | notesでの対応方針 |
|---|---|---|
| ルーティング/ディレクトリ再編コスト | 物理ファイルパス・URLパス・ナビ階層が密結合していたため、分野の再編のたびに大規模な一括修正が必要だった | 最初から「コンテンツ実体(`content/pages/`)・URLテーブル(`routes.ts`)・ナビ階層(`nav.ts`)」の3層分離で始める(Atlasが移行済みの構成をそのまま踏襲) |
| ページ数・連番のハードコード | 「全38ページ」「20/23」のような総数・連番をあちこちに手書きし、増減のたびにズレて放置された | 総数・全体連番の表現はそもそも使わない。連番バッジは単一の配列・グリッド内で完結するものに限定する |
| nav.ts記載漏れによる孤立ページ | ページを追加してもナビ構造への追記を忘れると、ビルドは通るが辿り着けないページになる | 新規ページ追加時に「コンテンツファイル・ルーティングテーブル・ナビ階層」の3箇所を必ず更新する運用を明文化する。可能であれば整合性検証スクリプトをCI/pre-commitに用意する |
| セクション間のコンテンツ重複 | 「工程軸」と「主題軸」の両方でディレクトリを持ち、同じ話題が二重管理になった | 主題(トピック)と工程(プロセス)を最初から別軸と意識し、同じ話題を2箇所に置きそうな場合は片方を「入口リンクのみ」にするルールを先に決めておく |
| 設計ドキュメントの陳腐化 | 実装変更後にドキュメントの更新が追いつかず、乖離したまま放置された | ディレクトリ構成やコンポーネント方針を変えるコミットには、関連ドキュメントの更新(または「現状と乖離済み」の一言追記)をセットで含める |
